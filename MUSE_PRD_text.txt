MUSE • Product Requirements Document Page 2 1. Product overview Product name:  MUSE Meaning:  A muse is a source of inspiration. The name represents a place where creative people find ideas, share their work and inspire one another. Tagline:  Find your inspiration. Share your creation. Product category:  Creative social networking platform. Product vision:  Build a welcoming online space where creators can present their work, discover new ideas, receive constructive feedback and form meaningful creative connections. Target audience λ Graphic designers and UI/UX designers. λ Web developers and software students. λ Photographers, illustrators and digital artists. λ Students, hobbyists and creative beginners. λ Independent creators looking for inspiration, feedback and collaboration. Core product principles λ Creativity first:  Give projects and ideas the main stage. λ Community over popularity:  Encourage meaningful interaction, not only follower counts. λ Welcoming by design:  Make it easy for beginners to participate. λ Clear ownership:  Users control and manage their own profiles and projects. λ Trust and privacy:  Protect user data with authentication and database access policies. 2. Goals and success criteria Primary goals λ Allow users to register, log in and manage a creator profile. λ Allow creators to publish, edit, delete and save project drafts. λ Help users discover projects and creators through search and categories. λ Support likes, comments, follows and bookmarks. λ Provide creative challenges and project submissions. λ Show useful notifications for community activity. λ Provide a personal portfolio view for each creator. Acceptance criteria λ All 16 planned pages load and navigate correctly. λ The layout is responsive on desktop, tablet and mobile. λ Authentication and data operations use Supabase, not simulated success messages. λ Users can only modify records they own.

MUSE • Product Requirements Document Page 4 3. Brand and design system Visual direction:  Warm Creative Studio  — friendly, editorial, expressive and polished. The interface should feel like a thoughtfully curated creative community, not a generic admin dashboard. Token Value Usage Warm Ivory #F7F4EC Main page backgrounds and spacious sections Soft Sage #A8B5A0 Primary buttons, selected states and calm accents Terracotta #C8795A Highlights, badges and important calls to action Sand Beige #DCCBB8 Borders, secondary panels and soft surfaces Deep Olive #343B35 Primary text, navigation and strong contrast Typography and components λ Headings:  Playfair Display. λ Body text:  DM Sans. λ Cards:  Rounded corners, subtle shadows, consistent spacing and clear image hierarchy. λ Buttons:  Sage as the primary action color; terracotta as a restrained accent. λ Navigation:  Consistent brand mark, page links and account actions. λ Motion:  Gentle hover transitions and subtle entrance effects; respect reduced-motion preferences. λ Accessibility:  Semantic HTML, visible focus states, useful labels, keyboard-friendly controls and readable contrast. Avoid λ Excessive gradients, overly dark full-page backgrounds and visual clutter. λ Tiny text, low-contrast labels and hover-only interactions. λ Unrelated styles between pages or inconsistent navigation. λ Fake buttons that look functional but do nothing. 4. Technical architecture Technology Role / constraint HTML5 Semantic page structure; one HTML file per page. CSS3 Theme, layouts, reusable components and responsive styling. Vanilla JavaScript Page behavior, validation, navigation and Supabase operations. Supabase JS SDK v2 Browser client for authentication and permitted database/storage operations. Supabase Auth Signup, login, logout, password reset and session handling. Supabase PostgreSQL Persistent relational application data. Supabase Storage Creator avatars and project images.

MUSE • Product Requirements Document Page 8 7. Supabase data model The following tables form the planned relational model. The coding agent must generate the final SQL migration scripts, constraints, indexes, triggers/functions where needed, RLS policies and Storage policies after reviewing the completed implementation. Table Important fields / purpose profiles User ID linked to auth.users; username, full name, bio, avatar URL, skills, website and social links. projects Owner, title, description, category, tools, cover image, external URL, draft/published status and timestamps. project_images Project reference, image URL and display order. likes User and project relationship; unique pair prevents duplicate likes. comments Author, project, comment content and timestamps. follows Follower and following profile IDs; unique pair and no self-follow. bookmarks User and saved project relationship; unique pair. challenges Title, description, category, cover, start date, deadline and status. challenge_submissions Challenge, creator, submitted project and description. notifications Recipient, actor, event type, related project/comment, message, read state and timestamp. Security and data rules λ Enable Row Level Security on every user-related table. λ Public users may read only public profile data and published projects. λ Users may create/update/delete only records they own, subject to the feature's rules. λ Bookmarks and notifications must be visible only to their owner/recipient. λ Do not allow browser clients to create arbitrary notifications for other users. λ Validate project ownership before accepting images or challenge submissions. λ Use Supabase Storage buckets for avatars and project media, with owner-scoped upload policies. λ Never expose the Supabase service_role key in client-side HTML or JavaScript. Storage plan Bucket Contents Policy direction muse-avatars Profile pictures Authenticated users upload/update files only in their own user-specific folder. muse-projects Project covers and gallery images Authenticated project owners upload media; public reads only for media attached to published projects where intended. 8. Search, discovery and moderation λ Search project titles, descriptions, categories and creator usernames.

Privacy, security and accessibility λ Use HTTPS in deployment and Supabase's public client key only in the browser. λ Enforce data access in Supabase RLS; hiding buttons in the UI is not security. λ Do not store plaintext passwords or sensitive secrets in localStorage. λ Use safe DOM rendering for user-generated content; avoid unsafe HTML insertion. λ Add labels, alt text, keyboard access and visible focus styles. λ Provide confirmation and clear feedback for important account/project actions. λ Add a privacy policy and community guidelines before public launch.

Local development and preview λ Open the MUSE folder in VS Code. λ Install/use the Live Server extension. λ Open index.html with Live Server to preview the site in a browser. λ Use relative file paths so pages work when opened from the project folder. λ Test at desktop, tablet and mobile widths after each page. λ Use public image URLs during early layout work; migrate uploads to Supabase Storage when that feature is implemented. 13. Coding-agent working agreement λ Build one page at a time; do not generate all 16 pages in one uncontrolled step. λ Before each new page, inspect existing files and reuse the established theme/components. λ Do not unexpectedly redesign existing pages or remove working features. λ Keep HTML, CSS and JS in separate files. λ Explain each changed/created file and provide exact local preview instructions. λ Test navigation, forms, responsive behavior and console errors before declaring a page complete. λ Do not claim a Supabase feature works until it has been tested with a connected project. 14. Supabase handover — important instruction The user wants the coding agent to prepare the Supabase setup instructions at the end, after the application code and database design are ready. Do not ask the user to run SQL commands now. λ At the final integration stage, the coding agent must provide one complete, reviewed SQL script (or clearly ordered migration scripts) for all required tables, relationships, indexes, constraints, triggers/functions and RLS policies. λ The agent must separately provide Storage bucket creation and upload/read policy instructions. λ The agent must list the exact Supabase Dashboard steps and identify where the project URL and anon/publishable key go. λ The agent must clearly identify which actions the user must perform manually in Supabase and in what order. λ The agent must never ask the user to paste a service_role key into frontend code. λ The user will apply the supplied commands/instructions only after the agent has provided them, then share any errors for troubleshooting.
